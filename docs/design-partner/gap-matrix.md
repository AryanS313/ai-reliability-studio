## Reading the matrix

The two tables join on gap ID: the first captures prioritization and the second captures the solution, verification scope, and acceptance evidence. Severity describes consequence, not observed incident frequency. Frequencies below are workflow exposure hypotheses inferred from code; no customer incident-rate data exists. Effort is a relative planning estimate: S = focused change, M = several related changes, L = multi-system or external work. It is not a measured time sheet.

Priority follows the requested order: **P0 security/privacy/isolation or misleading evidence; P1 broken critical workflows; P2 activation and interpretation; P3 repeat use and accessibility; P4 visual refinement; P5 additional scope**. Already working versioned assets, synthetic scenarios, retrieval, adapters, calibration UI, comparisons, exports, and CLI were preserved and corrected where needed.

Evidence sources: [security review](security-review.md), [core workflow audit](workflow-audit.md), [provider verification](provider-verification.md), and the specified test files. [Product brief](product-brief.md) cites the visited primary research and alternative-tool documentation. Product outcomes are not inferred from test counts.

## Remaining work by decision type

### Release blockers

Any failing security/integrity invariant, failed critical local workflow, unresolved applicable critical/high dependency vulnerability, or incomplete final integrated verification remains a blocker. The release review is authoritative about current delivery and check results, including scoped browser dependency exceptions. This matrix does not declare success from focused tests alone.

Claims that an independent first-time user understands the product, a real customer assistant is integrated, or this beta has demonstrated domain accuracy/adoption require external evidence. These are **blocked claims and pilot-validation prerequisites**, not facts that local polish can establish. Publication was authorized and completed; it does not establish these customer outcomes.

### Design-partner follow-ups

Run the approved actual endpoint and credential locally; review representative cases and held-out labels; measure the unassisted sample and real setup; exercise real upload formats/accessibility; complete two releases and collect de-identified outcome evidence. The [discovery plan](discovery-plan.md) defines recruitment and decision rules. Targets are hypotheses until measured.

### Enterprise-production requirements

Managed identity/provisioning and ingress, current managed PostgreSQL/RLS validation, durable jobs/storage, monitoring/alerting, malware scanning/parser isolation and optional OCR, bounded-load/recovery tests, retention/backup/restore operations, and formal assurance remain separate infrastructure work. The exact deployment must be verified before accepting data that depends on these controls.
